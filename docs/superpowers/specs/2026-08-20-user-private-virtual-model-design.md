# 用户私有虚拟模型设计规格

## 1. 目标与范围

在 new-api 中新增用户侧“虚拟模型”功能，将 autoapi 的候选链、候选级失败规则、冻结、循环尝试和流式预提交探测语义移植到 new-api，同时复用 new-api 的 WebUI 风格、API Key 鉴权、限流、日志、审计、内部模型调用和计费能力喵。

第一期只提供用户私有虚拟模型，不提供共享模型、公共模板、跨用户可见性或管理员代管模型喵。

虚拟模型是独立功能，不注册为普通 Group、Ability、Channel.Models 或普通模型目录中的真实模型，不复用现有 Token.AutoRoutes 作为其持久化载体喵。

## 2. 已确认的产品决策

- 虚拟模型入口位于登录用户侧左侧导航，沿用当前 new-api 的导航、路由和页面组件风格，不放入 Admin 导航组喵。
- 用户只能读取、修改、删除和查看自己创建的虚拟模型，用户之间允许使用相同名称喵。
- 请求名称采用 `virtual/<name>`，名称只允许 ASCII 字母、数字、短横线和下划线，系统按用户维度执行唯一性校验喵。
- 请求先完成 API Key 鉴权，再根据已认证用户和 `virtual/<name>` 查询模型，并检查该 API Key 是否具有显式绑定关系喵。
- 新建虚拟模型默认不绑定任何 API Key，用户必须显式授权后才能调用喵。
- `GET /v1/models` 只返回当前 API Key 已授权且仍启用的用户虚拟模型喵。
- 虚拟模型保存即生效，不设计草稿与发布流程喵。
- 请求开始时读取不可变配置快照，后续编辑、删除或撤销授权只影响新请求，已经开始的请求继续使用原快照完成喵。
- 删除采用普通二次确认，确认后彻底删除模型、候选、规则、授权关系和内联加密凭据，同时只保留不可还原的审计元数据喵。
- 用户可以单独启用或停用候选，也可以手动冻结和解除冻结候选喵。
- 候选链允许混合 new-api 内部候选和用户自定义上游候选喵。
- 虚拟模型不固定声明协议族；请求到达时保留客户端原始协议语义，不做 OpenAI 与 Anthropic 之间的主动转换喵。
- 自定义候选沿用 autoapi 当前已验证的 OpenAI 与 Anthropic 透传能力，候选必须实际兼容当前请求的 path、query、body、stream 和响应格式喵。

## 3. 请求调用语义

### 3.1 总体流程

```text
客户端请求 model=virtual/<name>
  -> new-api API Key 鉴权、限流和用户状态检查
  -> 按 owner_user_id + normalized_name 查询虚拟模型
  -> 检查 API Key 绑定关系与模型启用状态
  -> 创建本次请求的不可变配置快照
  -> 按候选顺序执行
  -> 根据候选规则执行 retry / next / freeze / passthrough
  -> 候选链耗尽后立即失败，或进入配置的循环模式
  -> 记录路由、审计、响应和内部候选消费结果
```

所有用户侧读写接口都必须使用服务端认证得到的用户 ID 作为所有者条件，不能信任客户端传入的 owner ID，也不能先按全局名称查询后再补做权限判断喵。

### 3.2 new-api 内部候选

内部候选由“分组 + 真实模型”组成，例如 `default + gpt-4o` 喵。

内部候选执行时必须等价于用户直接调用该分组中的该真实模型，完整复用 new-api 原有的 Channel 选择、priority、weight、自动禁用、协议适配、请求重试、额度预留、usage 解析、日志和计费流程喵。

虚拟模型层不读取、不固定、不冻结具体 Channel，也不重复实现 Channel 级重试；内部调用最终成功或最终失败后，虚拟模型层才根据候选规则决定是否转到下一候选喵。

内部候选产生的每一次实际可计量调用都独立执行额度预留与结算；失败候选已经产生 usage 时，即使最终响应来自后备候选，也必须按真实上游模型和实际 usage 独立结算喵。

### 3.3 用户自定义候选

自定义候选内联保存 Base URL、API key、真实模型名、认证方式和候选级超时，URL 与 API key 由服务端加密保存，前端、日志、审计和状态接口只显示脱敏摘要喵。

自定义候选执行时沿用 autoapi 透传语义，保留客户端原始 path、query、请求体和协议结构，只替换候选需要替换的认证信息与顶层 `model`，不把自定义上游注册为 new-api Channel 喵。

自定义候选不参与 new-api 额度预留、模型定价或消费扣费，相关供应商费用由用户自行承担；系统只记录脱敏路由、耗时、失败分类、冻结和结果审计喵。

自定义凭据只在发送请求的最短生命周期内解密使用，解密失败、凭据缺失、URL 非法或认证方式不支持时必须安全失败并记录脱敏错误喵。

### 3.4 流式不可逆边界

自定义流式候选必须在任何客户端可见字节写出前进行有限预提交探测，缓冲并识别有效内容、工具调用、正常结束、流内 error、空流、心跳、静默超时和总超时喵。

探测成功后必须回放缓冲区并继续使用同一个上游迭代器，不能通过重新读取响应体或重新发起请求造成内容丢失或重复喵。

一旦任何有效业务内容已经发送给客户端，虚拟模型层不得再切换候选、循环或无感重放；后续异常只能结束当前流并记录状态喵。

## 4. 候选失败规则与状态

每个候选独立保存有序失败规则，系统按照规则顺序从上到下匹配，命中第一条规则后停止继续匹配喵。

规则支持 HTTP 状态码、网络失败、超时、流式异常、响应体正则和 Retry-After 等 autoapi 失败条件，并支持 `retry`、`next`、`freeze`、`passthrough` 四种动作喵。

每个候选独立设置最大重试次数；候选级 `retry` 只直接驱动自定义上游候选，且受该候选最大重试次数限制喵。

内部候选的 Channel 重试和自动禁用完全由 new-api 原生机制处理，虚拟模型规则不得再对同一 Channel 失败重复施加一套无条件重试喵。

`retry` 在预算内重试当前自定义候选，`next` 立即推进下一候选，`freeze` 先写入自动冻结再推进下一候选，`passthrough` 立即结束并返回当前错误喵。

规则没有命中时必须使用明确的默认策略，默认策略不能依赖未校验的错误字符串；错误分类、HTTP 状态、受限响应摘要、是否已经向客户端写出内容和请求可重放性应结构化传入决策器喵。

候选有三种独立状态来源：用户启停、手动冻结、自动冻结喵。

停用候选会跳过该候选但保留其配置；手动冻结由用户设置到期时间并可手动解除；自动冻结由规则或自动避险触发并按 TTL 到期，任何一种有效停用或冻结存在时，后续新请求都不得选择该候选喵。

自动冻结按“同一用户 + 规范化 Base URL 摘要 + API key 不可逆指纹 + 真实模型 + 认证方式”共享，因此同一用户在多个虚拟模型中复用相同自定义节点时会共同避开该节点；不同用户之间绝不共享冻结状态喵。

内部候选不由虚拟模型层建立自动冻结，继续遵循 new-api 原生 Channel 可用性与自动禁用机制喵。

## 5. 循环尝试模式

每个虚拟模型可以独立设置是否启用循环模式、请求总超时和最大循环轮数，同时系统必须保留不可关闭的安全上限喵。

循环模式每一轮都从候选一开始，按原始顺序执行，并跳过手动停用、手动冻结、自动冻结和其他当前不可用候选喵。

当所有候选暂时不可用时，如果存在将在模型剩余总超时内到期的自动冻结，系统等待最近的自动冻结到期后再从候选一开始；手动停用和手动冻结不会被循环自动解除或强行等待喵。

如果没有可等待的自动冻结、等待时间超出剩余总超时、客户端取消请求、达到总超时或达到最大循环轮数，系统立即返回最终错误喵。

已经向客户端发送有效流内容后，循环模式立即失效，禁止后续候选切换喵。

## 6. 持久化数据模型

建议新增以下独立实体，具体 ORM 命名可按 new-api 现有模型惯例调整喵。

- `VirtualModel`：保存所有者、规范化名称、显示名称、启用状态、循环开关、总超时和最大循环轮数喵。
- `VirtualModelCandidate`：保存所属模型、稳定顺序、来源类型、启用状态、最大重试次数和候选级超时喵。
- `VirtualModelInternalCandidate`：保存 new-api 分组名和真实模型名喵。
- `VirtualModelCustomCandidate`：保存加密 URL、加密 API key、凭据版本、真实模型名、认证方式和超时喵。
- `VirtualModelFailureRule`：保存候选 ID、规则顺序、匹配条件、动作、冻结时长和版本喵。
- `VirtualModelTokenBinding`：保存虚拟模型 ID 与 Token/API Key ID 的显式授权关系喵。
- `VirtualModelManualFreeze`：保存候选 ID、操作者、冻结开始和到期时间喵。
- `VirtualModelCustomFreezeState`：保存用户隔离后的自定义候选身份、自动冻结到期、连续失败数和最近失败类别喵。
- `VirtualModelAuditLog`：保存资源 ID、所有者、操作者、动作、时间和不可还原的脱敏摘要喵。

虚拟模型与候选的唯一约束必须包含所有者维度；至少保证 `(owner_user_id, normalized_name)` 唯一，允许不同用户拥有同名模型喵。

删除操作使用事务删除模型、候选、规则、绑定关系和加密凭据；审计日志不能保留 URL、API key、请求体、完整规则正文或完整上游错误正文喵。

## 7. WebUI 与 API

### 7.1 WebUI

“虚拟模型”作为普通用户左侧一级入口，页面必须复用当前 new-api WebUI 的导航、TanStack file-based 路由、`SectionPageLayout`、表格、筛选、Drawer、Dialog、表单校验、拖拽排序、状态徽标和移动端布局喵。

页面采用列表 + 详情 Tabs 结构，第一期至少提供“概览”“候选链”“API Key 授权”“运行状态”四个区域，不创建 Admin 风格独立工作区或营销式卡片界面喵。

虚拟模型列表只显示当前用户自己的模型，支持名称搜索、启用状态筛选、候选数量、可用候选状态和最近失败摘要喵。

候选链使用可排序列表；候选编辑显示来源、分组与模型或自定义 URL/模型、启停、最大重试次数、规则数量、冻结状态和脱敏凭据喵。

API Key 授权区域只列出当前用户自己的 API Key；虚拟模型页和 API Key 编辑页修改同一份绑定关系，新建虚拟模型默认无绑定喵。

所有提交操作必须保留服务端校验错误，前端校验只能用于即时反馈；URL、认证、名称、正则、超时、重试次数和冻结时长必须在服务端再次验证喵。

### 7.3 调用接口的稳定请求与响应契约

虚拟模型调用不新增专用协议转换接口。客户端继续使用 new-api 已支持的原始 OpenAI 或 Anthropic 请求路径和请求体喵。

- OpenAI 例如 `POST /v1/chat/completions`，Anthropic 例如 `POST /v1/messages`；请求体顶层必须包含字符串 `model` 喵。
- `model` 的唯一虚拟模型形式为 `virtual/<name>`，`<name>` 必须匹配 `[A-Za-z0-9_-]{1,64}`；服务端规范化时统一转为小写喵。
- `stream` 只有顶层 JSON 布尔值 `true` 才启用流式；虚拟模型层不改变其他字段的流式语义喵。
- 请求的 path、query、请求体字段、协议事件和响应字节保持原协议语义；虚拟模型层只替换上游地址、出站认证信息和顶层 `model` 喵。
- 自定义候选必须使用与当前请求相同的 path、query、body、`stream` 和响应协议；不因候选配置而主动转换 OpenAI 与 Anthropic 协议喵。

`GET /v1/models` 只返回当前 API Key 已显式绑定、虚拟模型仍启用且当前灰度开关允许的模型；每个虚拟模型使用 `id=virtual/<name>`，不返回候选、真实模型、Base URL、协议能力、凭据摘要或其他用户资源喵。

用户侧控制面成功响应至少包含 `id`、`name`、`display_name`、`enabled`、`loop_enabled`、候选数量、`version`、创建时间和更新时间；候选只返回来源、顺序、启停、超时、重试次数、规则数量、冻结状态和脱敏摘要喵。

控制面错误统一包含 `code`、`message`、`field_errors` 和 `request_id`；`field_errors` 只能包含可操作且不泄露凭据的字段级摘要喵。


```text
GET    /api/virtual-models
POST   /api/virtual-models
GET    /api/virtual-models/:id
PUT    /api/virtual-models/:id
DELETE /api/virtual-models/:id
PUT    /api/virtual-models/:id/candidates
PUT    /api/virtual-models/:id/key-bindings
POST   /api/virtual-models/:id/candidates/:candidateId/freeze
DELETE /api/virtual-models/:id/candidates/:candidateId/freeze
GET    /api/virtual-models/:id/status
GET    /api/virtual-models/:id/audit-log
```

所有接口必须通过当前登录用户或 API Key 认证得到所有者，不接受客户端指定其他 owner；不存在、未授权和非本人资源统一采用不泄露资源存在性的错误策略喵。

请求分发在 API Key 鉴权后识别 `virtual/<name>`；模型查询必须包含所有者条件和绑定关系条件喵。

`GET /v1/models` 在完成 API Key 鉴权后追加当前 Key 已绑定且仍启用的 `virtual/<name>`，不返回其他用户或当前用户未授权的虚拟模型喵。

## 8. 接口、错误与安全约束

### 8.1 默认决策与校验边界

- 规则按顺序首条命中；规则没有命中时默认动作固定为 `next`，不依赖未校验的错误字符串喵。
- 候选级最大重试次数默认值为 `0`，表示只尝试一次；自定义候选总尝试次数上限为 4 次喵。
- 流式探测缓冲上限为 2 MiB，静默超时默认 60 秒且不得超过 300 秒，放流前总预算默认 300 秒且不得超过 600 秒喵。
- 单候选冻结时长不得超过 86400 秒，循环最大轮数不得超过 10 轮，虚拟模型总超时不得超过 1800 秒；超过硬上限的配置保存时返回结构化校验错误，不静默截断喵。
- 名称、URL、认证方式、正则、动作、超时、重试次数和冻结时长由服务端统一校验喵。
- 自定义 URL 默认只允许 HTTPS 和 443 端口；默认拒绝回环、链路本地、内网、无法解析主机和危险非标准端口，以降低 SSRF 风险喵。
- 自定义候选认证方式只允许已实现并测试通过的 Bearer、`x-api-key` 和 Anthropic `x-api-key` 语义喵。

### 8.2 用户 API 错误契约

- 所有资源接口使用认证得到的用户 ID；请求体中的 owner 字段不得覆盖认证身份喵。
- 资源不存在、他人资源和当前 API Key 未绑定统一返回 `404` 与 `virtual_model_not_found`，不泄露资源存在性喵。
- 功能关闭的新 `virtual/` 请求返回 `404` 与 `virtual_model_disabled`；普通模型和 Token.AutoRoutes 不受影响喵。
- 请求体非法、缺少字符串 `model` 或名称格式非法返回 `400` 与 `virtual_model_invalid_request`；数据库、配置或密钥服务不可用返回 `503` 与 `virtual_model_unavailable` 喵。
- 写接口支持版本冲突检测，过期版本返回 `409` 与 `virtual_model_version_conflict`；保存、授权、冻结和删除成功前必须完成事务提交喵。

### 8.3 加密凭据与生命周期

- 自定义 URL 和 API key 使用 new-api 服务端配置的主密钥进行信封加密保存；主密钥不得写入数据库、日志、前端包或普通备份，缺少主密钥时禁止启动自定义候选执行喵。
- 密文必须带版本、随机 nonce 和完整性校验标签；解密失败视为候选不可用，不允许尝试使用原始密文或降级为明文喵。
- 前端只接收协议、主机脱敏摘要、真实模型名、认证方式和凭据是否已配置；任何列表、状态、日志、审计和错误响应都不得返回完整 URL、query 中的 key 或 API key 喵。
- 请求创建不可变配置快照时锁定候选配置和授权状态；自定义候选凭据只在该请求的最短发送生命周期内解密到内存，响应结束、取消或失败后立即释放引用喵。
- 删除或撤销授权只影响尚未创建快照的新请求；已创建快照的请求可以继续使用其请求生命周期内已解密的凭据，但不得把凭据写入持久化日志、缓存或异步队列喵。
- 删除事务完成后仅保留不可还原的审计元数据和请求关联 ID；审计不得保存密文、明文凭据、请求体、完整规则正文或完整上游错误正文喵。

### 8.4 快照、关闭与回滚

- 快照至少包含虚拟模型启用状态、候选顺序及配置、规则版本、循环参数、授权检查结果、功能开关状态和请求关联 ID；快照创建完成后不再读取已删除或已修改的数据库记录喵。
- 功能开关关闭只阻止关闭之后创建的 `virtual/` 请求；已经完成鉴权并创建快照的请求继续执行，流式请求仍遵守放流后不可切换边界喵。
- 回滚只恢复功能开关和控制面配置的可用性，不恢复已被用户删除的凭据或已完成的审计记录；回滚动作本身必须写审计事件喵。
- 配置、数据库或密钥服务不可用时，新请求采用拒绝优先策略；已经创建快照的请求只依赖自身快照和已建立的上游连接，不重新读取控制面喵。

## 9. 接口、页面与可观测性

### 9.1 用户 API

用户侧接口采用以下稳定资源语义，具体路径遵循 new-api 当前路由前缀喵：

```text
GET    /api/virtual-models
POST   /api/virtual-models
GET    /api/virtual-models/:id
PUT    /api/virtual-models/:id
DELETE /api/virtual-models/:id
PUT    /api/virtual-models/:id/candidates
PUT    /api/virtual-models/:id/key-bindings
POST   /api/virtual-models/:id/candidates/:candidateId/freeze
DELETE /api/virtual-models/:id/candidates/:candidateId/freeze
GET    /api/virtual-models/:id/status
GET    /api/virtual-models/:id/audit-log
```

列表接口返回分页结果，详情接口返回脱敏配置和资源版本；候选、规则、绑定和冻结更新接口使用整体替换或带版本的事务更新，不能出现只保存半条候选链的中间状态喵。

运行状态只返回候选序号、来源类型、真实模型或分组摘要、启停/冻结状态、最近失败分类、耗时和时间戳；不得返回 Channel key、自定义 API key、完整 Base URL 或完整上游错误正文喵。

调用日志必须使用同一个虚拟请求 ID 关联入口请求、每次候选尝试、内部消费记录、自定义候选结果、最终响应和审计事件；结构化日志只允许记录脱敏摘要喵。

## 10. 迁移、开关与回滚

new-api 应作为唯一运行时配置源，不直接复用 autoapi 的 YAML 热重载、REPL 或独立 FastAPI 服务喵。

阶段一允许完成数据库、用户控制面、加密、审计和 WebUI，但虚拟模型总开关默认关闭，控制面保存不等于数据面可调用喵。

只有 API Key 认证、owner 隔离、授权查询、不可变快照、候选执行器、冻结作用域、错误契约和 `/v1/models` 过滤全部通过集成测试后，才允许开启虚拟模型调用喵。

如提供 autoapi 配置导入，必须由受控服务端或离线命令执行，批量校验 URL、认证、正则、动作、超时、候选链和名称后在一个事务中提交；任一配置非法则整批回滚喵。

新增系统级虚拟模型功能开关，并可独立控制自定义上游、循环模式和流式预提交探测；关闭功能时现有普通模型与 Token AutoRoutes 不受影响喵。

关闭功能开关后，新的 `virtual/` 请求立即拒绝，已经取得配置快照的运行中请求继续完成；回滚不物理删除配置、凭据、绑定或审计数据喵。

## 10. 非目标

第一期不实现共享虚拟模型、公共模板、管理员代管模型、跨用户资源查看、跨协议主动转换、用户自定义 Channel 资源池、WebSocket 自动故障转移、异步任务重复提交治理或按虚拟模型固定价格结算喵。

第一期不修改现有 Token.AutoRoutes 的存储格式和既有用户配置语义；现有 AutoRoutes 继续作为 new-api 原生 Token 级模型链功能独立运行喵。

## 12. 实施现状与剩余工作

本节记录截至 2026-08-22 的实现状态，作为后续开发、测试和上线验收的剩余工作清单喵。

### 12.1 已落地能力

- 已建立独立的 `VirtualModel`、候选、内部候选、自定义候选、失败规则、API Key 绑定、手动冻结、自动冻结和审计数据实体，并接入常规与快速数据库迁移喵。
- 已实现用户隔离的基础 CRUD、候选链读取、API Key 绑定写入、候选手动冻结/解冻、运行状态读取和审计日志读取路由喵。
- 已实现 `virtual/<name>` 在普通 Channel 选择前的识别、按 owner 与 API Key 授权查找、基础执行快照、`/v1/models` 可见性过滤和模型详情路径兼容喵。
- 已实现内部候选将真实模型与分组交给 new-api 原生 relay 的基础路径；内部候选不保存或暴露具体 Channel 喵。
- 已实现自定义候选的 AES-GCM 凭据加密、凭据指纹、HTTPS/443 校验、DNS/IP SSRF 防护、禁止环境代理与自动重定向、请求/响应敏感头过滤、顶层模型替换和非 2xx 预提交失败结构化处理喵。
- 已实现失败分类、首条规则匹配、默认 `next`、重试退避和自动冻结的基础服务层逻辑喵。
- 已实现用户侧虚拟模型入口、列表、概览、主模型创建/编辑/删除、候选链页签、API Key 授权页签和运行状态页签的基础 WebUI 喵。
- 正在实现候选链编辑器与 API Key 多选授权编辑器：支持内部/自定义候选、上移下移、启停、超时、重试次数、认证方式，以及自定义上游 API Key 永不回显的安全语义喵。

### 12.2 控制面剩余工作

- 候选链整体替换接口必须补充显式 `version` 请求字段与服务端 CAS 校验，避免两个浏览器会话以过期配置相互覆盖喵。
- 在未引入候选、规则和冻结的差异更新接口前，整体替换候选链会删除关联失败规则与手动冻结；WebUI 必须在保存前明确警告并要求确认，后端响应也应明确返回该影响喵。
- 推荐后续把候选更新拆为“保留候选 ID 的差异更新”或“候选链版本化整体替换”，以使同一候选的规则、冻结和审计关联可持续保留喵。
- 自定义候选编辑需支持“省略 `api_key` 表示保留已加密凭据”的受控差异更新契约；在该契约完成前，前端保存含既有自定义候选的完整候选链时必须要求重新输入每个 API Key，且绝不回显旧值喵。
- 失败规则的创建、读取、更新、删除、排序、验证与规则命中预览 API 尚未完成；候选页需要提供规则数量、规则编辑器和第一条命中顺序的可见说明喵。
- 手动冻结/解冻需要补充幂等语义、最大冻结时长、到期时间、当前操作者、冲突处理和完整状态响应；页面需要显示冻结来源、到期时间并提供可访问的解冻操作喵。
- 审计当前不能宣称覆盖所有配置和运行事件；应记录模型、候选、规则、绑定、冻结、功能开关、调用开始、每次尝试与最终结果的脱敏事件喵。
- `GetVirtualModelStatus` 当前的 `available_candidates` 仅接近“启用候选数量”，不等价于实时上游可用性；需改为明确的状态字段或在界面中避免将它表述为健康检查结果喵。
- 用户侧 API Key 选择器当前仅初始读取有限数量的 Key；后续需支持搜索、分页加载并清晰处理禁用、过期、耗尽或无权限 Token 喵。
- 写入接口与 WebUI 必须统一提取 Axios 服务端 `message`、`code` 和 `409 virtual_model_version_conflict`，冲突后刷新详情并保留可恢复的用户编辑提示喵。

### 12.3 数据面与候选编排剩余工作

- 内部候选进入原生 relay 后，必须能够在原生 Channel 级重试最终失败时把结构化结果交回虚拟模型编排器，由编排器根据失败规则选择 `next`、`freeze` 或 `passthrough`；不得把内部候选最终失败直接写死为客户端最终响应喵。
- 自定义候选的凭据缺失、解密失败、URL 校验失败、DNS 解析失败、请求体无法处理、建连失败和读取失败都必须在尚未提交响应时转换为候选级结构化失败，允许规则驱动后备候选；不得提前向客户端写最终错误喵。
- 必须完成循环模式：严格执行总超时、最大轮数、候选从首项重启、跳过停用与冻结候选、等待最近可在剩余预算内到期的自动冻结，并正确响应客户端取消喵。
- 自动冻结成功后的清理必须使用候选身份与版本/到期条件进行原子比较，避免一个请求成功时错误清除另一个并发请求刚写入的冻结喵。
- 内部候选应继续复用 new-api 的 Channel 选择、协议适配、额度预留、usage 解析、日志与结算；虚拟层只消费其最终结构化成功或失败结果，不复制 Channel retry 喵。
- 内部候选每次真实上游调用必须独立关联 usage、预留和结算；即使该候选失败后由后备候选成功，只要产生 usage 仍必须结算喵。
- 自定义候选的请求和响应只记录脱敏摘要，不参与 new-api 额度预留、模型定价或消费扣费喵。
- 每个虚拟请求、候选尝试、内部消费、上游结果、最终响应和审计事件必须通过 request ID、virtual request ID 与 candidate attempt ID 关联喵。

### 12.4 流式兼容性剩余工作

- 必须完成放流前探测器：在同一上游响应 iterator 上实现有限缓冲、静默超时、总预算、UTF-8 跨分块处理、SSE 事件解析、有效业务字节识别和缓冲回放喵。
- 探测器必须覆盖 OpenAI 与 Anthropic 的非流式和流式成功、HTTP 成功状态内的错误事件、空流、心跳、工具调用、thinking/reasoning、finish reason、usage 和流内错误喵。
- 一旦任何有效业务字节写给客户端，后续读取错误只能静默结束流并记录事件；不得切换候选、循环、重新发送上游请求，或向已开始的 SSE/HTTP 响应追加 JSON 错误喵。
- 放流前的失败才允许依据失败规则进行 retry、next、freeze 或 passthrough；实现应明确记录是否已提交响应，防止错误分支突破不可逆边界喵。

- 补充 WebUI API 与组件测试：候选新增、排序、删除、输入校验、自定义 Key 不回显与必填、保存警告、API Key 空解绑、无效 Token、服务端错误、409 冲突和移动端布局喵。

## 13. 完成定义

在以下全部条件满足前，虚拟模型功能仅视为“基础控制面与部分运行时已实现”，不得标记为完整交付喵。

1. 所有控制面写操作具备所有者隔离、输入校验、脱敏响应、乐观锁或等价的并发保护、事务原子性和完整审计喵。
2. 内部与自定义候选均能按同一候选编排语义返回结构化结果，失败规则、冻结、循环、超时和取消行为符合本规格喵。
3. 流式请求在放流前允许安全切换，在放流后严格禁止切换或追加协议外错误喵。
4. 内部候选计费、失败 usage 结算和全部运行时关联 ID 完整可追踪；自定义候选不产生 new-api 消费扣费喵。
5. `/v1/models`、模型详情、普通 relay 和 Token.AutoRoutes 的既有行为均通过回归测试且未改变喵。
6. 控制面 WebUI 已覆盖候选、规则、冻结、授权、状态、审计、删除确认和移动端场景，且不会显示或覆盖自定义上游明文凭据喵。
7. 数据库升级、单元测试、集成测试、流式兼容测试、前端检查与上线回滚演练均已完成并保留可审计结果喵。
