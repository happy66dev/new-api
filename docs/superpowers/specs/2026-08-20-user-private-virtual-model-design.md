# 用户私有虚拟模型设计规格

## 1. 目标与范围

在 new-api 中新增用户侧“虚拟模型”功能，将 autoapi 的候选链、候选级失败规则、冻结、循环尝试和流式预提交探测语义移植到 new-api，同时复用 new-api 的 WebUI 风格、API Key 鉴权、限流、日志、审计、内部模型调用和计费能力喵。

第一期只提供用户私有虚拟模型，不提供共享模型、公共模板、跨用户可见性或管理员代管模型喵。

虚拟模型是独立功能，不注册为普通 Group、Ability、Channel.Models 或普通模型目录中的真实模型，不复用现有 Token.AutoRoutes 作为其持久化载体喵。

## 2. 已确认的产品决策

- 虚拟模型入口位于登录用户侧左侧导航，沿用当前 new-api 的导航、路由和页面组件风格，不放入 Admin 导航组喵。
- 用户只能读取、修改、删除和查看自己创建的虚拟模型，用户之间允许使用相同名称喵。
- 请求名称采用 `virtual/<name>`，名称只允许 ASCII 字母、数字、短横线和下划线，系统按用户维度执行唯一性校验喵。
- 请求先完成 API Key 鉴权，再根据已认证用户和 `virtual/<name>` 查询模型，并检查该 API Key 是否具有显式绑定关系喵。
- 新建虚拟模型默认不绑定任何 API Key，用户必须显式授权后才能调用喵。
- `GET /v1/models` 只返回当前 API Key 已授权且仍启用的用户虚拟模型喵。
- 虚拟模型保存即生效，不设计草稿与发布流程喵。
- 请求开始时读取不可变配置快照，后续编辑、删除或撤销授权只影响新请求，已经开始的请求继续使用原快照完成喵。
- 删除采用普通二次确认，确认后彻底删除模型、候选、规则、授权关系和内联加密凭据，同时只保留不可还原的审计元数据喵。
- 用户可以单独启用或停用候选，也可以手动冻结和解除冻结候选喵。
- 候选链允许混合 new-api 内部候选和用户自定义上游候选喵。
- 虚拟模型不固定声明协议族；请求到达时保留客户端原始协议语义，不做 OpenAI 与 Anthropic 之间的主动转换喵。
- 自定义候选沿用 autoapi 当前已验证的 OpenAI 与 Anthropic 透传能力，候选必须实际兼容当前请求的 path、query、body、stream 和响应格式喵。

## 3. 请求调用语义

### 3.1 总体流程

```text
客户端请求 model=virtual/<name>
  -> new-api API Key 鉴权、限流和用户状态检查
  -> 按 owner_user_id + normalized_name 查询虚拟模型
  -> 检查 API Key 绑定关系与模型启用状态
  -> 创建本次请求的不可变配置快照
  -> 按候选顺序执行
  -> 根据候选规则执行 retry / next / freeze / passthrough
  -> 候选链耗尽后立即失败，或进入配置的循环模式
  -> 记录路由、审计、响应和内部候选消费结果
```

所有用户侧读写接口都必须使用服务端认证得到的用户 ID 作为所有者条件，不能信任客户端传入的 owner ID，也不能先按全局名称查询后再补做权限判断喵。

### 3.2 new-api 内部候选

内部候选由“分组 + 真实模型”组成，例如 `default + gpt-4o` 喵。

内部候选执行时必须等价于用户直接调用该分组中的该真实模型，完整复用 new-api 原有的 Channel 选择、priority、weight、自动禁用、协议适配、请求重试、额度预留、usage 解析、日志和计费流程喵。

虚拟模型层不读取、不固定、不冻结具体 Channel，也不重复实现 Channel 级重试；内部调用最终成功或最终失败后，虚拟模型层才根据候选规则决定是否转到下一候选喵。

内部候选产生的每一次实际可计量调用都独立执行额度预留与结算；失败候选已经产生 usage 时，即使最终响应来自后备候选，也必须按真实上游模型和实际 usage 独立结算喵。

### 3.3 用户自定义候选

自定义候选内联保存 Base URL、API key、真实模型名、认证方式和候选级超时，URL 与 API key 由服务端加密保存，前端、日志、审计和状态接口只显示脱敏摘要喵。

自定义候选执行时沿用 autoapi 透传语义，保留客户端原始 path、query、请求体和协议结构，只替换候选需要替换的认证信息与顶层 `model`，不把自定义上游注册为 new-api Channel 喵。

自定义候选不参与 new-api 额度预留、模型定价或消费扣费，相关供应商费用由用户自行承担；系统只记录脱敏路由、耗时、失败分类、冻结和结果审计喵。

自定义凭据只在发送请求的最短生命周期内解密使用，解密失败、凭据缺失、URL 非法或认证方式不支持时必须安全失败并记录脱敏错误喵。

### 3.4 流式不可逆边界

自定义流式候选必须在任何客户端可见字节写出前进行有限预提交探测，缓冲并识别有效内容、工具调用、正常结束、流内 error、空流、心跳、静默超时和总超时喵。

探测成功后必须回放缓冲区并继续使用同一个上游迭代器，不能通过重新读取响应体或重新发起请求造成内容丢失或重复喵。

一旦任何有效业务内容已经发送给客户端，虚拟模型层不得再切换候选、循环或无感重放；后续异常只能结束当前流并记录状态喵。

## 4. 候选失败规则与状态

每个候选独立保存有序失败规则，系统按照规则顺序从上到下匹配，命中第一条规则后停止继续匹配喵。

规则支持 HTTP 状态码、网络失败、超时、流式异常、响应体正则和 Retry-After 等 autoapi 失败条件，并支持 `retry`、`next`、`freeze`、`passthrough` 四种动作喵。

每个候选独立设置最大重试次数；候选级 `retry` 只直接驱动自定义上游候选，且受该候选最大重试次数限制喵。

内部候选的 Channel 重试和自动禁用完全由 new-api 原生机制处理，虚拟模型规则不得再对同一 Channel 失败重复施加一套无条件重试喵。

`retry` 在预算内重试当前自定义候选，`next` 立即推进下一候选，`freeze` 先写入自动冻结再推进下一候选，`passthrough` 立即结束并返回当前错误喵。

规则没有命中时必须使用明确的默认策略，默认策略不能依赖未校验的错误字符串；错误分类、HTTP 状态、受限响应摘要、是否已经向客户端写出内容和请求可重放性应结构化传入决策器喵。

候选有三种独立状态来源：用户启停、手动冻结、自动冻结喵。

停用候选会跳过该候选但保留其配置；手动冻结由用户设置到期时间并可手动解除；自动冻结由规则或自动避险触发并按 TTL 到期，任何一种有效停用或冻结存在时，后续新请求都不得选择该候选喵。

自动冻结按“同一用户 + 规范化 Base URL 摘要 + API key 不可逆指纹 + 真实模型 + 认证方式”共享，因此同一用户在多个虚拟模型中复用相同自定义节点时会共同避开该节点；不同用户之间绝不共享冻结状态喵。

内部候选不由虚拟模型层建立自动冻结，继续遵循 new-api 原生 Channel 可用性与自动禁用机制喵。

## 5. 循环尝试模式

每个虚拟模型可以独立设置是否启用循环模式、请求总超时和最大循环轮数，同时系统必须保留不可关闭的安全上限喵。

循环模式每一轮都从候选一开始，按原始顺序执行，并跳过手动停用、手动冻结、自动冻结和其他当前不可用候选喵。

当所有候选暂时不可用时，如果存在将在模型剩余总超时内到期的自动冻结，系统等待最近的自动冻结到期后再从候选一开始；手动停用和手动冻结不会被循环自动解除或强行等待喵。

如果没有可等待的自动冻结、等待时间超出剩余总超时、客户端取消请求、达到总超时或达到最大循环轮数，系统立即返回最终错误喵。

已经向客户端发送有效流内容后，循环模式立即失效，禁止后续候选切换喵。

## 6. 持久化数据模型

建议新增以下独立实体，具体 ORM 命名可按 new-api 现有模型惯例调整喵。

- `VirtualModel`：保存所有者、规范化名称、显示名称、启用状态、循环开关、总超时和最大循环轮数喵。
- `VirtualModelCandidate`：保存所属模型、稳定顺序、来源类型、启用状态、最大重试次数和候选级超时喵。
- `VirtualModelInternalCandidate`：保存 new-api 分组名和真实模型名喵。
- `VirtualModelCustomCandidate`：保存加密 URL、加密 API key、凭据版本、真实模型名、认证方式和超时喵。
- `VirtualModelFailureRule`：保存候选 ID、规则顺序、匹配条件、动作、冻结时长和版本喵。
- `VirtualModelTokenBinding`：保存虚拟模型 ID 与 Token/API Key ID 的显式授权关系喵。
- `VirtualModelManualFreeze`：保存候选 ID、操作者、冻结开始和到期时间喵。
- `VirtualModelCustomFreezeState`：保存用户隔离后的自定义候选身份、自动冻结到期、连续失败数和最近失败类别喵。
- `VirtualModelAuditLog`：保存资源 ID、所有者、操作者、动作、时间和不可还原的脱敏摘要喵。

虚拟模型与候选的唯一约束必须包含所有者维度；至少保证 `(owner_user_id, normalized_name)` 唯一，允许不同用户拥有同名模型喵。

删除操作使用事务删除模型、候选、规则、绑定关系和加密凭据；审计日志不能保留 URL、API key、请求体、完整规则正文或完整上游错误正文喵。

## 7. WebUI 与 API

### 7.1 WebUI

“虚拟模型”作为普通用户左侧一级入口，页面必须复用当前 new-api WebUI 的导航、TanStack file-based 路由、`SectionPageLayout`、表格、筛选、Drawer、Dialog、表单校验、拖拽排序、状态徽标和移动端布局喵。

页面采用列表 + 详情 Tabs 结构，第一期至少提供“概览”“候选链”“API Key 授权”“运行状态”四个区域，不创建 Admin 风格独立工作区或营销式卡片界面喵。

虚拟模型列表只显示当前用户自己的模型，支持名称搜索、启用状态筛选、候选数量、可用候选状态和最近失败摘要喵。

候选链使用可排序列表；候选编辑显示来源、分组与模型或自定义 URL/模型、启停、最大重试次数、规则数量、冻结状态和脱敏凭据喵。

API Key 授权区域只列出当前用户自己的 API Key；虚拟模型页和 API Key 编辑页修改同一份绑定关系，新建虚拟模型默认无绑定喵。

所有提交操作必须保留服务端校验错误，前端校验只能用于即时反馈；URL、认证、名称、正则、超时、重试次数和冻结时长必须在服务端再次验证喵。

### 7.2 用户 API

建议新增用户侧接口如下，实际路径应遵循 new-api 当前路由约定喵。

```text
GET    /api/virtual-models
POST   /api/virtual-models
GET    /api/virtual-models/:id
PUT    /api/virtual-models/:id
DELETE /api/virtual-models/:id
PUT    /api/virtual-models/:id/candidates
PUT    /api/virtual-models/:id/key-bindings
POST   /api/virtual-models/:id/candidates/:candidateId/freeze
DELETE /api/virtual-models/:id/candidates/:candidateId/freeze
GET    /api/virtual-models/:id/status
GET    /api/virtual-models/:id/audit-log
```

所有接口必须通过当前登录用户或 API Key 认证得到所有者，不接受客户端指定其他 owner；不存在、未授权和非本人资源统一采用不泄露资源存在性的错误策略喵。

请求分发在 API Key 鉴权后识别 `virtual/<name>`；模型查询必须包含所有者条件和绑定关系条件喵。

`GET /v1/models` 在完成 API Key 鉴权后追加当前 Key 已绑定且仍启用的 `virtual/<name>`，不返回其他用户或当前用户未授权的虚拟模型喵。

## 8. 迁移、开关与回滚

new-api 应作为唯一运行时配置源，不直接复用 autoapi 的 YAML 热重载、REPL 或独立 FastAPI 服务喵。

如提供 autoapi 配置导入，必须由受控服务端或离线命令执行，批量校验 URL、认证、正则、动作、超时、候选链和名称后在一个事务中提交；任一配置非法则整批回滚喵。

新增系统级虚拟模型功能开关，并可独立控制自定义上游、循环模式和流式预提交探测；关闭功能时现有普通模型与 Token AutoRoutes 不受影响喵。

关闭功能开关后，新的 `virtual/` 请求立即拒绝，已经取得配置快照的运行中请求继续完成；回滚不物理删除配置、凭据、绑定或审计数据喵。

## 9. 测试验收标准

后端单元测试必须覆盖名称规范化、跨用户同名隔离、API Key 绑定与撤销、运行中请求快照、候选排序、启停、手动冻结、自动冻结、冻结共享范围、规则优先级、候选重试次数、循环轮数、总超时、自动冻结等待和客户端取消喵。

执行器测试必须覆盖内部候选完全复用 new-api 原生调用、自定义候选透传 path/query/body、认证替换、顶层模型替换、OpenAI 与 Anthropic 非流式和流式请求、429 Retry-After、网络错误、HTTP 200 内嵌 error、空流、心跳、流内 error、跨 chunk UTF-8、工具调用、放流前切换和放流后禁止切换喵。

计费测试必须覆盖内部候选逐次动态预留、失败但有 usage 的独立结算、无 usage 不扣费、自定义候选不扣 new-api 额度、混合候选多条内部消费记录及虚拟请求 ID 关联喵。

前端测试必须覆盖用户侧导航权限、列表筛选、候选拖拽、规则排序、授权双向编辑、脱敏凭据、删除确认、服务端错误呈现和移动端布局喵。

上线前必须完成密钥泄漏扫描、请求 ID 到候选尝试和消费日志的关联验证、流式字节兼容验证、循环上限验证和功能关闭回滚验证喵。

## 10. 非目标

第一期不实现共享虚拟模型、公共模板、管理员代管模型、跨用户资源查看、跨协议主动转换、用户自定义 Channel 资源池、WebSocket 自动故障转移、异步任务重复提交治理或按虚拟模型固定价格结算喵。

第一期不修改现有 Token.AutoRoutes 的存储格式和既有用户配置语义；现有 AutoRoutes 继续作为 new-api 原生 Token 级模型链功能独立运行喵。
